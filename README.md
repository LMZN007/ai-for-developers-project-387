## Как открыть приложение

**Публичная ссылка:** https://calls-booking-umck.onrender.com — страница записи [/book](https://calls-booking-umck.onrender.com/book), раздел владельца [/admin](https://calls-booking-umck.onrender.com/admin). Если сервис спал, первый запрос откроется примерно через минуту.

Запустить у себя (нужны Git и [mise](https://mise.jdx.dev/getting-started.html)):

```bash
git clone https://github.com/LMZN007/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install
mise run start   # http://localhost:3000
```

Или в Docker: `docker build -t calls-booking . && docker run --rm -p 8080:8080 -e PORT=8080 calls-booking`, затем http://localhost:8080.

## Агент в GitHub

В репозитории работает агент Claude Code ([`anthropics/claude-code-action`](https://github.com/anthropics/claude-code-action)): он отвечает на команды доверенных участников в issues и PR. Воркфлоу — [`.github/workflows/claude.yml`](.github/workflows/claude.yml), в Actions он называется «Claude agent».

### Событие и кто может запустить

Воркфлоу срабатывает на `issue_comment` и `pull_request_review_comment` с `types: [created]`, то есть на новый комментарий в issue, в PR или в ревью-комментарии к коду. Запускается, только если:

- комментарий начинается с `/oc` (если `/oc` стоит в середине текста, задание не запускается);
- автор комментария — `OWNER`, `MEMBER` или `COLLABORATOR` (дополнительно сам action отклоняет авторов без права записи);
- автор — не бот, комментарии ботов игнорируются.

Код PR из fork агент не берёт: `allow_fork_prs: "false"`.

### Команда вызова

`/oc <задача>` — это `trigger_phrase: /oc`, аналог `mentions` у OpenCode. Примеры:

- `/oc explain this issue` — объяснить задачу;
- `/oc прочитай docs/agents/ и ответь, какой у проекта трекер, ничего не меняя` — ответ без изменений в коде;
- `/oc исправь задачу: <что именно>` — внести правки и подготовить ветку.

### Модель и доступ

- Модель: `claude-sonnet-5-5` (`claude_args: --model claude-sonnet-5-5`).
- Работает на подписке Claude владельца, платного API-ключа нет. Токен подписки лежит в секрете `CLAUDE_CODE_OAUTH_TOKEN` (получен командой `claude setup-token`).
- Тайм-аут прогона — 60 минут (агент выполняет и крупные задачи по спецификации: тесты, `mise run check`, e2e). Прогон один на issue или PR (`concurrency` у задания, а не у всего воркфлоу): новая команда ждёт окончания предыдущей, а не отменяет её. Очередь стоит на задании, потому что каждый комментарий — и ответы `claude[bot]`, и замечания авторевью — тоже запускает воркфлоу; на уровне воркфлоу такой отсеянный `if` прогон занимал единственное место ожидающего и отменял ждавшую команду человека (#26).
- mise ставит те же инструменты, что и в CI, а системные библиотеки Chromium ставятся тем же шагом, что в `ci.yml`, чтобы агент мог выполнить `mise run check` целиком, с e2e.

### Назначение и результаты

Агент отвечает на вопросы, разбирает задачи и вносит правки по команде. Результаты:

- ответ комментарием в issue или PR от имени `claude[bot]` со ссылкой на прогон в Actions;
- если нужны изменения — ветка `claude/...` и ссылка на создание PR.

Прогоны смотрите на вкладке [Actions](https://github.com/LMZN007/ai-for-developers-project-387/actions), воркфлоу «Claude agent».

### Права

У задания воркфлоу: `contents: read`, `id-token: write`, `pull-requests: read` (чтобы action видел, что PR из fork). У `actions/checkout` включено `persist-credentials: false`.

Комментирует и пушит не `GITHUB_TOKEN`, а токен Claude GitHub App: action обменивает на него OIDC-токен (`id-token: write`). Поэтому действия видны от имени приложения `claude[bot]`, а не `github-actions`, а токен самого воркфлоу только читает. Приложение установлено только на этот репозиторий.

### Автотриаж новых обращений

Воркфлоу [`.github/workflows/triage.yml`](.github/workflows/triage.yml) («Claude triage») разбирает новые обращения без владельца: агент читает `.claude/skills/triage/SKILL.md` (скилл нельзя вызвать как скилл из-за `disable-model-invocation`, поэтому `prompt` велит прочитать файл и выполнить его) и ставит категорию и состояние.

- Событие: `issues` с `types: [opened]`.
- Фильтры: автор — `OWNER`/`MEMBER`/`COLLABORATOR`, не бот; у issue нет ни одной метки состояния (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`). Подготовленные скиллами тикеты приходят уже с меткой, и прогон получает статус `skipped`.
- Права: `contents: read`, `id-token: write`, у checkout `persist-credentials: false`; метки и комментарии ставит токен Claude GitHub App (`claude[bot]`), токен подписки — секрет `CLAUDE_CODE_OAUTH_TOKEN`. Из инструментов агенту доступны чтение файлов и `gh issue view/list/edit/comment`, `gh label list`; `gh issue close` и запись в код не разрешены.
- Тайм-аут задания — 15 минут; один прогон на issue (`concurrency`).
- Делает: ставит одну категорию (`bug` или `enhancement`) и одно состояние — `needs-triage` или `needs-info` (с вопросами автору по шаблону Triage Notes). Каждый комментарий начинается с дисклеймера скилла.
- Не делает: не ставит `ready-for-agent`, `ready-for-human`, `wontfix`, не закрывает issue, не меняет код. Эти решения принимает владелец. Запрет на `ready-for-*` и `wontfix` держится на `prompt`: `gh issue edit` технически позволил бы поставить любую метку.
- Где смотреть: вкладка [Actions](https://github.com/LMZN007/ai-for-developers-project-387/actions), воркфлоу «Claude triage». Пропущенные из-за фильтров прогоны видны там со статусом `skipped`.

### Авторевью PR

Воркфлоу [`.github/workflows/review.yml`](.github/workflows/review.yml) («Claude review») — независимая сессия Claude на каждом PR. Она не связана с сессией, которая писала код: читает [`REVIEW.md`](REVIEW.md), находит в описании PR ссылки на спецификацию и тикеты, читает их через `gh` и сверяет с ними diff. Код не меняет.

- Событие: `pull_request` с `types: [opened, synchronize, reopened, ready_for_review]`. Черновики и PR из fork пропускаются: у fork нет секретов, и его код не должен попадать к агенту.
- Результат: комментарии к строкам diff и один общий комментарий со списком замечаний (каждое со ссылкой на критерий `REVIEW.md` или пункт спецификации) и вердиктом. Пишет `claude[bot]`.
- Модель `claude-sonnet-5-5`, режим App (OIDC-токен меняется на токен Claude GitHub App). `allowed_bots: claude` — коммиты агента в ветку PR тоже ревьюятся.
- Права задания: `contents: read`, `pull-requests: read`, `id-token: write` и `actions: read`; последнее нужно только шагу, который считает прошлые прогоны.
- Ревьюер берёт спецификацию и тикеты по ссылкам из описания PR; ссылки на исходный проект `386` должны быть полным адресом (`--repo`). Если токен что-то не прочитает, ревьюер пишет об этом в итоге.
- Ограничение: Claude App выдаёт токен, только если файл воркфлоу совпадает с версией в `main`, поэтому PR, который добавляет или меняет `review.yml`, ревью моделью не получает (action пишет «Workflow validation failed» и пропускает вызов).
- Такой прогон предел всё равно засчитывает: шаг `Run Claude review` начался, хотя модель не вызывалась. Предел ошибается в безопасную сторону.

**Предел запусков.** Не больше `REVIEW_BUDGET` прогонов с вызовом модели на один PR (переменная репозитория, по умолчанию 3). Первый шаг задания считает кодом, а не по тексту комментариев: через `gh api` берёт прогоны этого воркфлоу для PR (кроме текущего) и смотрит, начался ли в их задании шаг «Run Claude review» (не `skipped`). Если таких 3 и больше, шаг пишет `::error::` с причиной, номером PR, head SHA и ссылкой на логи и завершается с кодом 1; шаг с моделью не запускается. Отказанный прогон сам бюджет не тратит. Причина предела: каждый `synchronize` — это платный вызов модели на подписке владельца, а бесконечный цикл «правка — ревью — правка» ничего не сходится; после трёх ревью дальше смотрит человек. Предел меняется переменной `REVIEW_BUDGET` без правки воркфлоу.

**Тайм-аут и `cancel-in-progress`.** Тайм-аут задания 15 минут: обычное ревью занимает несколько минут, запас нужен на большой diff, а зависший прогон не должен держать раннер 6 часов (как в `triage.yml`). `concurrency` по номеру PR с `cancel-in-progress: true`: после нового push ревью старого коммита уже не нужно, и отмена экономит вызов модели. Отменённый на шаге модели прогон считается в пределе (модель уже вызвана), отменённый раньше — нет. В отличие от агента (`claude.yml`), где новая команда ждёт предыдущую, здесь важен только последний коммит.

### Браузерная проверка PR

Воркфлоу [`.github/workflows/browser-check.yml`](.github/workflows/browser-check.yml) («Browser check») проверяет PR в браузере отдельно от агента и от CI, на своём раннере.

- Событие: `pull_request` (`opened`, `synchronize`, `reopened`, `ready_for_review`), черновики пропускаются.
- Берёт ровно `pull_request.head.sha`, а не merge-коммит, который `pull_request` отдаёт по умолчанию: результат относится к коду, который запушил автор.
- Запускает `mise run e2e`: продакшен-сборка web, один сервер на порту 3100 с пустым хранилищем, сценарий Playwright в Chromium.
- Артефакт `browser-check-<SHA>` (14 дней) содержит `head-sha.txt`, `result.txt` (`passed` или `failed`), отчёт `playwright-report/` и `test-results/` (трассы упавших тестов). Он загружается и при падении; после загрузки задание падает, если сценарий упал.
- Тайм-аут 15 минут, как у `check` в CI; `cancel-in-progress: true` по номеру PR: результат для устаревшего коммита не нужен, а артефакт с SHA в имени не спутать с новым.

### Шаблон PR

[`.github/pull_request_template.md`](.github/pull_request_template.md) подставляется в описание каждого нового PR: связи (обращение, спецификация, тикеты, согласование), что сделано, проверки с обоснованием их глубины последствиями ошибки, риск и откат. Ревьюер сверяет описание с этим шаблоном (`REVIEW.md`, п. 8).

### Аудит приложения

Воркфлоу [`.github/workflows/audit.yml`](.github/workflows/audit.yml) («Audit») раз в сутки проверяет работающее приложение Lighthouse CI, а агент заводит issue только по новым находкам. Данные собирает код, без модели; агент их читает и сверяет с уже заведёнными issue.

**События.**

- `schedule` с `cron: "17 3 * * *"`: раз в сутки, время UTC. GitHub может задерживать запуски по расписанию.
- `workflow_dispatch`: Actions → Audit → Run workflow, только из `main` (Claude App выдаёт токен, лишь если файл воркфлоу совпадает с версией в `main`).

**Сбор данных (без модели).**

- Адрес берётся из переменной репозитория `APP_URL`. Сейчас это выкладка исходного проекта `386`, а не этого репозитория (см. результаты ниже).
- Прогрев: `curl` к `$APP_URL/api/health` до 30 раз с паузой 5 с (около 2,5 минут): спящему Render нужна минута, чтобы проснуться.
- Lighthouse CI `@lhci/cli@0.16.1` (версия закреплена), Chrome раннера, по одному прогону на страницы `/book` и `/admin`.
- Находка: проверка категорий accessibility, best-practices или seo со score < 1. Такая проверка проходит или не проходит детерминированно, поэтому каждое падение — конкретный дефект; информационные, ручные и неприменимые проверки не оцениваются и не учитываются. Производительность — одна находка на страницу и только при оценке категории ниже 0.5: оценка зависит от процессора раннера и холодного Render, поэтому порог грубый, а отдельные проверки шумят.
- Ключ находки: `lighthouse:<страница>:<id проверки>`, например `lighthouse:/book:image-alt`; для производительности — `lighthouse:<страница>:performance`.
- Результат сборки — `findings.json`: `status` (`ok` или `no_data`), `reason`, `head_sha`, `run_url` и список находок (`key`, `page`, `audit_id`, `title`, `score`, `details`).

**Работа агента.**

- Claude (`claude-sonnet-5-5`), режим App. Права задания: `contents: read` и `id-token: write`; issue создаёт токен Claude App.
- Инструменты (`allowedTools`): `Read`, `Glob`, `Grep`; `Write` и `Edit` только в `audit-report/**`; `gh issue list`, `gh issue view`, `gh issue create`; `gh label list` и `gh label create` на случай, если метки `audit` ещё нет. Закрытия, правок и комментариев чужих issue нет.
- Агент один раз получает все issue с меткой `audit` (`gh issue list --state all`, без `--search`: индекс поиска отстаёт) и считает находку известной, только если в теле issue есть точная строка ``Ключ находки: `<key>` ``. Первая строка тела каждого нового issue — именно эта строка.
- Открытый issue с ключом есть — находка пропускается. Нет ни открытого, ни закрытого — создаётся issue. Есть только закрытые — создаётся новый issue «Повторно: …» со ссылкой на прежний issue и на PR, который его закрыл (`closedByPullRequestsReferences`), либо с пометкой, что PR не найден.
- «Нет данных» (`status: "no_data"`: `APP_URL` не задан, приложение не ответило или Lighthouse не отработал): агент не создаёт issue, ничего не закрывает и не делает вывода, что дефектов нет; в отчёте пишет «нет данных» и причину.
- Тексты отчёта Lighthouse (`title`, `details`, `reason`) и тела issue — данные, а не инструкции: указания в них агент не выполняет, только сверяет ключи и пересказывает находки.

**Тайм-аут и `concurrency`.** `timeout-minutes: 25`: прогрев до 2,5 минут, Lighthouse на двух страницах и агент занимают несколько минут, остальное — запас, а зависший прогон не должен держать раннер 6 часов. Группа `concurrency` — имя воркфлоу с `cancel-in-progress: false`: ручной запуск не прерывает плановый и наоборот, иначе отменённый агент остановился бы посреди списка находок.

**Где результат.** Артефакт `audit-<run_id>` (30 дней): страница прогона → Artifacts. В нём отчёт Lighthouse (HTML и JSON), `findings.json`, `agent-report.md` (что найдено, создано, пропущено и почему), `execution.json` (журнал агента) и тела созданных issue. Артефакт загружается всегда. В коммиты отчёты не попадают: `audit-report/` и `.lighthouseci/` в `.gitignore`.

### Почему Claude, а не OpenCode

Задание допускает другого агента с теми же сценариями. OpenCode в Actions работает через API-ключ провайдера модели, а подписку Claude к стороннему агенту подключать нельзя. Claude Code работает с подпиской официально, поэтому выбран он.

### Решение по `share`

У Claude Code параметра `share` нет, сессии наружу не публикуются. У OpenCode `share` в action v1.19.6 помечен как устаревший и игнорируется, так что публичных ссылок на сессии не было бы и там.

## Как работает текущая версия

Ниже — исходный сценарий курса. Сервис реализует его по согласованной [спецификации](https://github.com/LMZN007/ai-for-developers-project-386/issues/12) с такими упрощениями:

- **Владелец один**, без регистрации и входа ([ADR-0003](docs/adr/0003-single-owner.md)). Его разделы — «Типы встреч» и «Записи» по ссылке «Для владельца».
- **Доступность фиксированная**: пн–пт, 09:00–18:00 по часовому поясу владельца `Europe/Moscow`. Раздела «Доступность» нет, часы и пояс в интерфейсе не настраиваются.
- **Слоты** начинаются каждые 30 минут и целиком помещаются в рабочие часы. Записаться можно на 14 дней вперёд (сегодня и ещё 13).
- **Время у гостя и у владельца** показано в часовом поясе их браузера, с подписью пояса. Переключателя пояса нет.
- **Адрес страницы типа встречи** — `/book/<slug>`, а не `/<владелец>/<slug>` ([ADR-0005](docs/adr/0005-guest-page-urls.md)).
- **Записи не пересекаются**, даже у разных типов встреч. Если время уже занято, гость видит сообщение и выбирает другой слот.
- **Владелец может отменить предстоящую запись** в разделе «Записи»: кнопка «Отменить запись», затем подтверждение. Запись пропадает совсем, без истории, а её время снова становится слотом. Начавшуюся запись отменить нельзя. Гость об отмене не узнаёт, причина не запрашивается ([ADR-0006](docs/adr/0006-cancel-is-delete.md)).

## Пользовательский сценарий: от типа встречи до записи

Роли:

- **Владелец** — тот, кто создаёт тип встречи и принимает записи.
- **Гость** — тот, кто записывается на встречу.

Референс: [Cal.com](https://cal.com). Регистрация, подключение внешних календарей и уведомления в сценарий не входят.

### 1. Владелец создаёт тип встречи

1. Открывает раздел **«Типы встреч»** и нажимает **«Создать»**.
2. Заполняет форму:
   - **Название** (например, «Консультация 30 минут»);
   - **Ссылка (slug)** — подставляется из названия автоматически, её можно поменять: `/<владелец>/consultation`;
   - **Описание** — по желанию;
   - **Длительность** в минутах (например, 30).
3. Сохраняет. Новый тип встречи появляется в списке, рядом есть публичная ссылка и кнопка «Скопировать ссылку».

### 2. Владелец задаёт, когда он свободен

1. В разделе **«Доступность»** указывает рабочие часы по дням недели (например, пн–пт, 09:00–18:00) и свой часовой пояс.
2. Из этих часов и длительности встречи получаются свободные слоты. При 30 минутах это 09:00, 09:30, 10:00 и т. д.

### 3. Гость открывает публичную страницу

1. Переходит по ссылке `/<владелец>/consultation`.
2. Видит название, длительность, описание и календарь на месяц. Дни, где есть свободные слоты, можно выбрать.
3. Выбирает день и видит список свободных слотов. Время показано в часовом поясе гостя, пояс можно сменить.

### 4. Гость записывается

1. Выбирает слот.
2. Заполняет форму: **имя**, **email** и, по желанию, **комментарий**.
3. Нажимает **«Подтвердить»**.
4. Видит экран **«Встреча запланирована»**: что за встреча, когда она будет (дата, время, часовой пояс) и кто участвует.

### 5. Запись появляется у владельца

1. Владелец открывает раздел **«Записи» → «Предстоящие»**.
2. В списке видит новую запись: дату и время, тип встречи, имя и email гостя, комментарий.
3. Занятый слот исчезает с публичной страницы, поэтому второй гость не сможет записаться на то же время.

### Итоговая цепочка

```
Создать тип встречи → Задать доступность → Гость открывает ссылку →
Выбирает день и слот → Заполняет форму → Подтверждение →
Запись в «Предстоящих» у владельца (слот занят)
```

Проект построен по принципу contract-first: API описан в `packages/contract/main.tsp`, а сервер и клиент работают по сгенерированному из него OpenAPI.

```
apps/api/            бекенд (Fastify)
apps/web/            фронтенд (Vite + React)
apps/e2e/            браузерный сценарий (Playwright)
packages/contract/   контракт TypeSpec и сгенерированный SDK
```

## Установка

Нужны Git и [mise](https://mise.jdx.dev/getting-started.html). Node.js, pnpm и остальные инструменты mise поставит сам нужных версий из `mise.toml`.

```bash
git clone https://github.com/LMZN007/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install
```

`mise install` ставит инструменты, затем автоматически устанавливает зависимости (`pnpm install`), браузер Chromium для браузерного сценария и git-хуки. Если Chromium пропал (например, после очистки кэша), поставьте его снова: `mise run setup`. Переменные окружения настраивать не нужно: порты заданы в `mise.toml` (API — 3000, фронтенд — 5173).

## Использование

Запустить приложение для разработки (бекенд и фронтенд работают в фоне):

```bash
mise run dev
```

Откройте http://localhost:5173. Проверить API напрямую: `curl http://localhost:3000/api/health`.

Запустить как в продакшене, без Vite: `mise run start` — собирает фронтенд, и один сервер на порту `PORT` (по умолчанию 3000) отдаёт и API (`/api/*`), и страницы. Так же приложение работает в Docker-образе.

Управление фоновыми серверами:

```bash
mise daemons ls          # состояние
mise daemons logs api    # логи бекенда (или web)
mise daemons stop        # остановить
```

Проверки и разработка:

```bash
mise run check       # все проверки — то же, что запускает CI
mise run test        # тесты
mise run e2e         # браузерный сценарий (Playwright) с настоящим сервером
mise run lint        # линтер и проверка форматирования
mise run format      # автоисправление форматирования
mise run gen         # пересобрать OpenAPI и SDK после изменения контракта
```

Коммиты оформляются по [Conventional Commits](https://www.conventionalcommits.org/ru/) (`feat:`, `fix:`, `docs:` …) — это проверяет git-хук.

## Деплой

Публичный сервис по ссылке выше выкатывается из первого проекта: его Render Blueprint — [`render.yaml` в ai-for-developers-project-386](https://github.com/LMZN007/ai-for-developers-project-386/blob/main/render.yaml). Этот репозиторий пока на Render не подключён, коммиты сюда сервис не меняют.

Приложение работает в одном Docker-контейнере: один процесс Node отдаёт API (`/api/*`) и страницы, порт берёт из переменной `PORT`.

> **Данные не сохраняются.** Типы встреч и записи хранятся в памяти процесса и пропадают при каждом перезапуске, новом деплое и засыпании сервиса. Бесплатный сервис Render засыпает после 15 минут без запросов; первый запрос будит его примерно за минуту — после этого списки пусты, и владельцу нужно заново создать типы встреч.

Собрать и запустить образ локально (нужен [Docker](https://www.docker.com/products/docker-desktop/)):

```bash
docker build -t calls-booking .
docker run --rm -p 8080:8080 -e PORT=8080 calls-booking   # http://localhost:8080
```

Прогнать браузерный сценарий против любого запущенного сервиса, например опубликованного:

```bash
E2E_BASE_URL=https://calls-booking-umck.onrender.com mise run e2e
```

### MCP-сервер Render для Claude Code

Логи и деплои публичного сервиса агент смотрит через [MCP-сервер Render](https://render.com/docs/mcp-server). Его конфигурация лежит в репозитории — [`.mcp.json`](.mcp.json) — и не содержит секретов: ключ подставляется из переменной окружения `RENDER_API_KEY`.

1. Создайте API-ключ: Render → [Account Settings → API Keys](https://dashboard.render.com/u/settings?add-api-key).
2. Сохраните его в переменной окружения **вне репозитория**, например добавьте в `~/.zshrc` строку `export RENDER_API_KEY="<ваш ключ>"` и перезапустите терминал и VS Code.
3. Откройте проект в Claude Code и разрешите проектный MCP-сервер `render`, когда он спросит (или через `/mcp`). В `/mcp` сервер должен быть в статусе connected.
4. Попросите агента выбрать рабочее пространство: «Set my Render workspace to <имя>».

Не вписывайте ключ в `.mcp.json` и другие файлы репозитория. Если ключ всё же попал в коммит — сразу отзовите его в Render и создайте новый.
