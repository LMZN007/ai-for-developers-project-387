# REVIEW.md

Критерии ревью PR сервиса «Календарь звонков». По ним независимая сессия Claude проверяет diff
(`.github/workflows/review.yml`); те же критерии годятся для ревью человеком. Каждое замечание
ссылается на пункт отсюда или на пункт спецификации, на которую ссылается PR.

Ревьюер читает, но не меняет код. Он пишет общий комментарий со списком замечаний и вердиктом
и комментарии к строкам diff там, где замечание привязано к коду.

## Критерии

### 1. Спецификация и тикеты

- В описании PR есть ссылка на спецификацию и на тикеты, которые он выполняет. Если ссылки нет,
  это замечание.
- Diff делает то, что сказано в спецификации и тикетах: основной, негативный и соседний сценарии,
  пользовательские истории, решения из «Implementation Decisions». Лишнего сверх них нет.
- Отклонение от спецификации названо в описании PR и согласовано; молчаливое отклонение — замечание.

### 2. Термины

- Тексты интерфейса, сообщения об ошибках и документация используют русские термины
  `GLOSSARY.md` (Тип встречи, Слот, Запись, Гость, Владелец, Доступность, Горизонт записи,
  Конфликт). Слова из списков _Avoid_ («бронирование», «событие», «клиент» и т. п.) — замечание.
- В коде и контракте термины называются по-английски по `AGENTS.md`: `EventType`, `Slot`, `Booking`,
  `guest*`, ответ 409 `time_conflict`; Доступность и Горизонт записи — константы в
  `apps/api/src/schedule.ts`.

### 3. Contract-first

- API меняется только через `packages/contract/main.tsp` ([ADR-0001](docs/adr/0001-contract-first-typespec.md)).
  Обработчик, маршрут или вызов из web без изменения контракта — замечание.
- Обработчики в `apps/api/src/handlers.ts` названы по `operationId`; web ходит в API только через SDK.
- Новые коды ошибок добавлены в перечень `ApiError.code` контракта.

### 4. Сгенерированные файлы

- `packages/contract/generated/` не редактируется и не попадает в коммиты.

### 5. Тесты

- Каждый сценарий спецификации (основной, негативные, соседний) покрыт тестом: API — в
  `apps/api/test/`, поведение в браузере — в `apps/e2e/tests/`.
- Тест проверяет поведение, а не реализацию, и упал бы без изменения. Тест, который проходит
  при сломанном коде, или удалённый без причины тест — замечание.
- Для каждого негативного теста ревьюер спрашивает: «прошёл бы он, если бы маршрута или
  обработчика не было?» Тест на 404 должен отличать «нет записи» от «нет операции»: например,
  сначала проверяет успешный ответ той же операции (204) на существующей записи. Если тест
  проходит без реализации — замечание.
- Граничные случаи терминов глоссария проверены: конец Записи не входит в Конфликт, Слот целиком
  внутри Доступности, граница Горизонта записи.

### 6. ADR

- Решение, которое трудно отменить, меняет прежнее решение или выбирает между вариантами, записано
  в `docs/adr/` по образцу существующих. PR не противоречит принятому ADR; если противоречит,
  ADR обновлён.

### 7. Тексты интерфейса

- Тексты по-русски, по терминам глоссария, без опечаток, одним стилем с соседними экранами.
- Состояния ошибки, загрузки и пустого списка показаны; сообщение об ошибке говорит, что делать.

### 8. Коммиты и PR

- Заголовки коммитов — Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`,
  `refactor:`; scope — `api`, `web`, `contract`).
- Коммит, который выполняет тикет, ссылается на него номером в конце заголовка: `feat(api): ... (#14)`.
- Описание PR заполнено по `.github/pull_request_template.md`; глубина проверок обоснована
  последствиями ошибки.
- Версии и `CHANGELOG.md` руками не правятся (их ведёт release-please); файлы
  `.github/workflows/hexlet-check.yml` и `.github/workflows/README.md` не тронуты.

### 9. Общее качество

- Нет отключённых правил линтера без узкой причины, секретов в коде, мёртвого кода и отладочного вывода.
- Воркфлоу: действия закреплены по SHA с комментарием версии, у заданий есть `timeout-minutes`
  и минимальные `permissions`.

## Как оформлять результат

1. Комментарии к строкам diff — для замечаний, привязанных к коду. В каждом: что не так, ссылка на
   критерий (например, «REVIEW.md, п. 3») или пункт спецификации, как исправить.
2. Общий комментарий — список замечаний (по важности, с теми же ссылками) и вердикт:
   **Можно мержить**, **Нужны правки** или **Нельзя мержить**. Если замечаний нет, так и пишут.
3. Что проверить не удалось (нет доступа к спецификации, diff обрезан), называют прямо, а не
   считают проверенным.
